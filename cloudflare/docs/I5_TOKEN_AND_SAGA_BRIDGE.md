# Checkout credential recovery and internal saga bridge

The browser creates a separate random 32-byte checkout token before submission. The user must save it before sending the prepare request. The token and customer data are never put in browser storage; D1 holds only the token hash. The original nonsecret draft key remains in localStorage. Recover an unknown prepare result by GET on the existing plan prepare path, with X-Plan-Token, X-Checkout-Key and X-Interop-Token headers. Recovery verifies the owner and exact checkout, returns redacted journal truth, never calls a provider, never creates a new checkout, and keeps the local lock. A lost token cannot be reconstructed; manual operator recovery is necessary. No automatic POST replay. A prepared row that already has saga operations cannot be replayed as NOT_STARTED.

New plan mutexes use a hash of the checkout key, so the internal bridge can verify the source lock belongs to the original preparation. Preexisting random I5 locks are deliberately not accepted for execution; they require operator review. If a D1 reserve attempt has an uncertain result, retain the plan mutex until recovery/operator review; do not assume the write failed.

The internal bridge is not imported by index.ts, orders.ts, plans.ts or packages.ts. It requires INTEROP_HOLDS=true, BOOKING_ENABLED=true, the plan owner credential, matching checkout key/token and source lock, and an injected server-owned per-action authorization callback. All clients resolve before mutation. HOLD and CONFIRM are separate, recovery is operator-only through the existing saga lock fence and quiescence requirement. The callback must be bound to real staging/release evidence before any future route wiring; test approval callbacks are fixture only. No flags changed, no real provider requests, no deployment. Legacy routes are unchanged. Operator unlock/reissue and route activation remain out of scope until staging and release approval.
