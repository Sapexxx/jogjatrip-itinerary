## Persistence model

- jt_checkout_requests: unique hashed checkout key, hashed caller-created 32-byte random access token, stable canonical request fingerprint, immutable normalized intent and trusted I2 offer snapshots. Shared externalRef = order ID JT- + 32 hex, within master 64-character limit. Client must generate and retain token before first request; never send token to provider, never log it. Same key/owner/intent returns same order even if ephemeral offer changes; different payload/owner returns conflict. New logical checkout with new key is not deduplicated; I5 must bind stable key to checkout UI and plan lock. Source plan/package authorization and native add-ons remain I5 integration concerns; I3 journal covers external provider items only. No legacy jt_orders row yet; I4/I5 must integrate existing order view and keep old order reads intact. Intent includes necessary customer data (existing D1 access controls); operation rows contain only hashes, stable operation key, sanitized result and error code. No raw PII in operation request journal. Retention/access policies must be defined before production.
- jt_order_locks: exclusive SQL CAS claim, fencing counter, lease, owner hash. No automatic takeover after expiry; stale executor could still have remote effects. Trusted recovery requires explicit quiescence verification and expected fence, recovery-only lock cannot create mutation intent. No public API for recovery in I3. Renew before expiry, release only with no unresolved operation. I4 must enforce ownership before every remote send; fencing alone does not fence a remote provider.
- jt_interop_operations: immutable request hash and stable per-order/item/operation key, intent IN_FLIGHT before side effect; duplicate begin returns created=false (never authorize new send), state CAS revision + live fence, SUCCEEDED/REJECTED/UNKNOWN. Confirm requires all holds durably successful; release/confirm mutually exclusive for same item in this conservative phase, no automatic release after confirm. No further operation while unresolved. Outcome projection validates exact identity/state, retains changed provider price for compensation, drops extra fields and raw errors. Exact hold body reconstructed from immutable checkout, explicit recovery replay demonstrated only in fixture; no automatic replay or provider mutation. I4 owns orchestration, price/TTL margin, status aggregation, partial/unknown and compensation decisions. A confirmed hold discovered after uncertain confirm must be reconciled before proceeding; no blind fallback.
